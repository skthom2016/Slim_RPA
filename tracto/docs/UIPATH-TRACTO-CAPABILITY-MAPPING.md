# UiPath → Tracto Capability Mapping

Research base: UiPath's own documentation (docs.uipath.com), product pages (uipath.com), and UiPath community forum threads, gathered November 2026. Tracto base: the current codebase (`orchestrator-go`, `desktop-runtime`, `browser-runtime`, `terminal-runtime`, `designer`) and its docs. Where a UiPath detail comes only from a third-party or forum source rather than official docs, that is marked.

UiPath is a very large commercial platform (Studio, Studio Web, Robot, Orchestrator, AI Center, Document Understanding, Action Center, Apps, Data Service, Insights, Process Mining, Task Mining, Test Suite, Integration Service, Marketplace, Automation Hub, Agent Builder/Autopilot). Tracto today is a focused desktop + browser + terminal RPA runtime with a Go orchestrator and a WPF designer. The tables below compare feature-by-feature, not product-by-product — most of UiPath's surface area has no Tracto counterpart yet, which is exactly what Tables 2 and 3 are for.

## Table 1 — UiPath features that already exist in Tracto (mapped)

| # | UiPath feature | UiPath capability | Tracto equivalent | Gap / notes |
|---|---|---|---|---|
| 1 | Studio — sequential workflow of activities | Drag-and-drop activities run top to bottom, with control flow (If, Switch, Loops) | **Script with ordered `steps[]`** (`app.launch`, `type`, `key`, `click`, …) run top to bottom | A script has **no If/Switch/loops, by design**: each script is a straight line. Repetition over rows is done outside the script (row 32); a decision per row is not built yet (Table 2 #1) |
| 2 | Studio — Assign / variables, string interpolation | Variables and arguments typed and scoped per workflow | **`${name}` variable substitution** in any parameter; `storeAs` namespaces step outputs; the Designer's validator now resolves every `${...}` reference against what earlier steps/segments actually produce and fails validation (`VAL-030`) on a reference nothing produces | Tracto variables are still untyped strings only, with no scoping, no arrays/objects — see Table 2 — but the build-time "undefined reference" check UiPath gets for free from typed variables is now present even without a type system |
| 3 | Studio — Delay / Wait activities | Fixed wait, or wait-for-element/wait-for-condition | **`delay` action** (ms, capped 30 s); browser runtime has `wait` (wait-for-visible with timeout) | Desktop runtime has no "wait until window appears" — only a fixed delay |
| 4 | Studio — Open Application / Start Process | Launches an application and attaches to its window | **`app.launch`** (desktop), **`navigate`** (browser) | Desktop `app.launch` fails on console apps, documents without a registered app, and already-running browsers — narrower than UiPath's |
| 5 | Studio — Type Into / Send Hotkey | Keyboard-driven input and shortcuts into a target window | **`type`**, **`key`** (desktop); **`fill`**, **`type`**, **`press`** (browser) | Desktop `type` cannot send Enter/Tab/Esc (must use `key`); no IME/non-ASCII support outside `notepad.type` |
| 6 | Studio — Click / Double Click / Hover | Mouse actions targeted by selector or image | **`click`** (desktop, coordinates/offset only — no selector); **`click`, `dblclick`, `hover`** (browser, selector-based) | Desktop click has **no UI selector at all** — only screen coordinates or window-relative offset, which is fragile; see Table 2 (selectors) |
| 7 | Studio — UI selectors (role/name targeting) | Targets elements by accessible attributes rather than coordinates | **Browser runtime element targeting**: `role`+`name`, `label`, `placeholder`, `testId`, `text`, `css`, `xpath` — ambiguous matches fail loudly (`TARGET_AMBIGUOUS`) | Desktop runtime has no equivalent — see Table 2 (UI Automation selectors for Win32/WPF apps) |
| 8 | Studio — Get Text / Get Attribute / data scraping | Reads values out of UI elements into variables | **`getText`, `getValue`, `getAttr`** (browser, with `storeAs`) | Desktop runtime has no way to read arbitrary on-screen/UI text into a variable (only `clipboard.get` and `file.read`) |
| 9 | Studio — Assertions / Verify Expression | Checks a condition and fails the test/run if false | **`assert`** (browser: `visible`, `enabled`, `checked`, `urlEquals`, `textEquals`) | No desktop-side assertion action |
| 10 | Studio — HTTP Request activity | Calls REST/SOAP APIs, parses JSON/XML response | **`http.get`, `http.post`** (desktop) with `storeAs` capturing status/body/json fields | Only top-level JSON fields are captured — no nested object/array access (Table 2) |
| 11 | Studio — Read Text File / File operations | Reads/writes/copies/moves/deletes files | **`file.read`** (desktop, text only, 5 MB cap); file copy/move/delete done via Run-dialog `cmd /c` recipes, not native activities | UiPath has native File activities (Copy, Move, Delete, Exists); Tracto does these only by shelling to `cmd` |
| 12 | Studio — Save Excel/Word output via UI | Keyboard-driven Save As into Office apps | **`file.saveAs`** (desktop, generic Save-As dialog driver, works for Notepad and similarly-shaped Save As dialogs) | Not Office-specific; no direct Excel/Word object-model access (Table 2) |
| 13 | Studio — Get/Set Clipboard | Reads or writes the OS clipboard | **`clipboard.get`** (desktop) | No `clipboard.set`; UiPath has both |
| 14 | Studio recording → workflow generation | Screen/web recorder generates activities from captured actions | **Designer recording** (desktop capture engine + browser CDP capture) → **Generate Draft** turns the transcript into steps, including batching repeated keypresses into a single `type` step; a session can now record a second segment after stopping the first without discarding it (Start resets a stopped session instead of being disabled) | Tracto's recorder is simpler — no explicit "recording modes" (basic/desktop/web/citrix) tuned per target the way UiPath's is |
| 15 | Studio — Image/OCR-based automation for VDI (Citrix, RDP) | Computer Vision activities read a streamed screen image via a neural network when selectors are unavailable | **None** — Tracto desktop runtime drives real Win32 windows/coordinates only | Full gap — Tracto has no screen-image/OCR targeting at all; see Table 2 |
| 16 | Studio — password/credential fields never recorded in plaintext | Workflows reference a Credential asset, never a literal password | **Browser recorder writes password fields as `${secret:NAME}`**, never literal text; browser runtime resolves `${secret:NAME}` from the worker's own environment variable and never logs it | Desktop runtime has no equivalent secret-reference mechanism yet (Table 2) |
| 17 | Orchestrator — job queue, scheduling, worker fleet | Assigns jobs to available robots; time-based and queue-based triggers | **Orchestrator-go**: `/jobs` queue, `/jobs/pull` (workers pull), `/admin/schedules` with a scheduler loop that fires cron schedules in a named time zone (per-schedule params, an overlap rule, and a grace window for fires missed during downtime; see `scheduling.md`), lease/heartbeat model, `LeaseExpiryMonitor`, `DeadlineMonitor`, `RestartRecovery` | No queue-*item*-triggered jobs (UiPath's "queue trigger" fires on new queue items; Tracto's "queue" is the job run queue itself, not a business-data queue — Table 2) |
| 18 | Orchestrator — artifact/package versioning | Workflows are packaged (`.nupkg`) and versioned per-folder | **Artifact store**: `PUT/GET/DELETE /artifacts/{id}/versions/{ver}`, with idempotent re-publish and mismatch checks (`422 INVALID_SCRIPT`) | No package *dependencies* or shared library packages (Table 2) |
| 19 | Orchestrator — multi-runtime job routing | Different robot types (attended/unattended/non-production) pick up different job types | **`targetRuntime` routing**: `desktop`, `browser`, `terminal` workers each pull only their own runtime's jobs; worker registration carries `runtimeType` | Routing is by runtime type only, not by robot *capability tags*, machine pools, or robot license type (Table 2) |
| 20 | Orchestrator — chained/multi-step automations (sequencing processes) | One process's output can feed another via queues, assets, or orchestration logic (built manually; no first-class "pipeline" object in classic Orchestrator) | **Segmented scripts**: one JSON with ordered `segments[]`, each with its own runtime (desktop → browser → terminal), parent/child runs, outputs flowing forward as `${param.<storeAs>.<field>}` | This is actually a **Tracto strength over UiPath's classic model** — segmented scripts are a cleaner first-class multi-runtime pipeline than most classic Orchestrator patterns (UiPath's closer analogue is Maestro, its newer process-orchestration layer, which is a separate, newer product) |
| 21 | Orchestrator — run status & telemetry API | REST endpoints to query job/run state and logs | **`GET /jobs/{runId}`**, **`GET /jobs/{runId}/telemetry`**, **`GET /admin/telemetry`** | No log *streaming*; no structured business-exception vs. system-exception distinction (Table 2) |
| 22 | Orchestrator — cancel a running job | Stop a job from the console/API | **`POST /jobs/{runId}/cancel`**, propagates to the active segment in a segmented run | — |
| 23 | Orchestrator — security/audit event logging | Logs auth failures, policy violations | **`AppendSecurityEvent`**, **`GET /admin/security-events`** | No full audit trail of *user* actions (who published/ran/deleted what) — only security events (auth failures) are logged; Table 2 |
| 24 | Orchestrator — webhooks/callback signing | Signed callbacks to external systems on job events | **HMAC-SHA256 signed `/callbacks`** (`ORCHESTRATOR_HMAC_KEYS`) | UiPath's equivalent (webhooks) supports more event types and a management UI; Tracto's is a single endpoint |
| 25 | Orchestrator — bearer-token authentication | JWT-based API authentication | **JWT auth middleware** on `/jobs`, `/workers`, `/admin` (HMAC-signed, dev-mode bypass when no signing key is set) | Single shared signing key, no per-user identity, no RBAC/roles/permissions — Table 2 |
| 26 | Orchestrator Web UI — dashboard | Monitor queues, jobs, robots from a browser | **Orchestrator UI** (Node/Express, port 4000), lists artifacts and lets you trigger a run (`▶ Run`) | Far smaller surface than UiPath's dashboard — no per-tenant/folder views, no queue analytics, no robot fleet view |
| 27 | Credential handling — never store secrets in the script | Credential assets resolved by the robot at runtime from a vault | **Browser profiles**: a named, persistent browser folder (`--login <profile>`) keeps a site signed in across runs without the script holding a password; **`${secret:NAME}`** resolves from a worker environment variable at runtime and is never logged | No actual *vault* integration (Azure Key Vault, CyberArk, HashiCorp Vault, AWS Secrets Manager) — secrets are plain environment variables on the worker machine (Table 2) |
| 28 | Studio — reusable, named recording sessions / profiles for browser login | Not a direct UiPath feature by this name, but conceptually close to attended "sign in once" patterns | **Shared signed-in browser profile**, chosen per segment via a dropdown ("Signed-in browser" / "Empty browser"), one profile per machine, locked while a browser window holds it open | This is a Tracto-specific convenience, not a direct UiPath port |
| 29 | Test Suite (classic: "RPA Testing") — simulate a run before publishing | A workflow can be executed as a test with pass/fail reporting | **Designer "Run Test"** (`IScriptTestRunner` local simulation) with per-step pass/fail and duration, reported in the Output pane | UiPath's Test Suite does *real* execution against test data sets with Test Manager case/suite tracking; Tracto's "Run Test" is a local simulation, not a real run against the target app (Table 2 clarifies the gap) |
| 30 | Studio — script/workflow signing before deployment | Not a standard UiPath feature (UiPath instead relies on package signing and Orchestrator access control) | **Script signing**: `Sign`/`Verify` commands produce an `HMAC-SHA256`/digest signature recorded against the script, checked before publish; the signature is now automatically dropped the moment the editor's script changes (new script loaded or started), so a stale signature can never carry into a later, different publish | Tracto-specific; not a UiPath parity item, listed here because it is a real control the Designer enforces |
| 31 | Studio — activity property/arguments panel (edit a step's inputs without re-recording) | Selecting an activity shows a typed properties grid of its arguments | **Step editor parameter grid**: selecting a step shows its action's required/optional parameters from an `ActionCatalog` (per action, per runtime), lets an author add, rename or remove parameter rows, and shows what data is available to reference (`${...}`) at that point via `DataFlow.AvailableTo` | Tracto's grid is untyped key/value rows, not a typed arguments form, and has no per-parameter validation beyond the reference check in row 2 |
| 32 | Studio — For Each Row in Data Table / For Each Excel Row | Loops over the rows of a data table or sheet and runs the same activities for each | **Row batches in sheet-service** (`POST /process/start`): a short main job starts a batch and ends; the Go service queues a published **child script** for each pending row, one at a time, waits for it, and writes the child's outputs, a `Status` of `Done` or `Failed`, and a message into that row. Works on `.xlsx`, Google Sheets and SharePoint/OneDrive workbooks. Run live against a real Orchestrator and browser worker for a browser child; cancel, timeout, restart and unreachable-Orchestrator cases are covered by automated tests | The loop runs in Go, not in the script. Rows run sequentially. A job never starts another job and waits for it, because a waiting job holds its worker and can deadlock; only Go waits. Items other than sheet rows (invoices in a PDF, files in a folder, records from an API) need a matching Go API that reads that source and queues the child the same way (Table 2 #24); the developer skills tell an author to say so and create it first. Not built: running items in parallel |
| 33 | Studio — Try Catch / per-item error handling and re-run of failed items | A failing item is caught, logged and the loop continues; failed items can be retried | A failed child marks only its own row `Failed`, with the runtime's error line in the message column, and **the other rows still run**. Starting the batch again processes only the rows whose `Status` is not `Done` | Retry is by starting the batch again, not automatic: no retry count, no back-off, no business-versus-system error type (Table 2 #5) |
| 34 | Studio — Read Cell / Write Cell without driving Excel | Reads and writes workbook cells through the Excel object model or a file API | **sheet-service** reads and writes cells, rows and ranges of `.xlsx`, Google Sheets and SharePoint/OneDrive workbooks, and `POST /cell` reads one cell by row and column; desktop scripts reach it with `http.post` | Excel and the two online sources only; no Word or PDF (Table 2 #13, #14). A local `.xlsx` must be closed in Excel while it is written |

## Table 2 — UiPath features NOT in Tracto today, but resolvable with a new/extended Go (or other) backend service

These are features where the underlying problem is solvable with server-side logic, a database, a queue, or an API — i.e., infrastructure the existing Go orchestrator (or a new companion service) could reasonably grow to cover. They do **not** require solving perception/AI problems that are out of scope for a backend service alone.

| # | UiPath feature | What it would take in Tracto | Backend approach | Effort/risk |
|---|---|---|---|---|
| 1 | **Control flow** (If/Switch/For Each/While loops, nested blocks) | Scripts stay straight lines and the format gets no `if` or `loop`. Every repeat and every decision is a **main job and a child job with a Go API between them**: the main job passes values to the API and ends, and the API queues the child (or the appropriate one of several children) and waits for it, so no job ever waits for another job. **Built:** For Each over sheet rows (Table 1 #32). **Not built:** (a) a **branch API**: Go checks a rule on the values it is given (from the main job, the row, or an earlier item's result) and queues child A, B or C, with a default for no match; (b) a row filter; (c) While/until with a maximum count; (d) a retry count per row; (e) a loop over a source that is not a sheet (Table 2 #24). The developer skills (desktop and browser) state this rule and tell an author that a missing API must be created first | Extend the Go service. A branch API takes the values in its request, refuses an unpublished child, replies at once, queues the chosen child through the Orchestrator, records which branch ran and why, and offers progress and cancel routes. No change to the script format, the three runtimes, the Designer or the validator | Low-medium per item. The design points are the rule language (a comparison on a string value is enough to start), the default branch, and keeping every wait in Go |
| 2 | **Typed variables, arrays, objects** | Replace string-only `${param.x}` substitution with a small typed value model (string/number/bool/array/object) carried through segments | Orchestrator stores/passes richer JSON instead of flat key-value; runtimes gain array/object indexing in expressions | Medium — mostly a data-model change; backward compatible if old string params still work. Partially de-risked already: the Designer's validator (`DataFlow`/`VAL-030`) now tracks, per step, exactly which names are in scope and flags unresolved references at authoring time — the scope-tracking half of this work is done, only the type model itself remains |
| 3 | **Business-data queues with per-item retry/status** (UiPath Queue Items, transaction retries) — *partly delivered:* the rows of a sheet batch (Table 1 #32) already carry a status (`Done`/`Failed`), an error message and rerun-only-unfinished; missing are a queue API, retry count, priority and several consumers | A `queue_items` table + API (`POST /queues/{name}/items`, `GET /queues/{name}/items/next`, status transitions: New → InProgress → Success/Failed, retry count, priority) — distinct from the existing job-run queue | New Go handler package + SQLite tables, following the existing artifact/run handler pattern | Low-medium — fits the orchestrator's existing architecture well; this is a natural, high-value extension |
| 4 | **Queue-item-triggered jobs** (start a run when a queue item arrives) | Once #3 exists, add a trigger type that watches a queue and enqueues a job per item, or per-batch | Extends `/admin/schedules` (cron) with a queue-trigger variant | Low, once #3 is built |
| 5 | **Business vs. system exception classification + configurable retry policy** — *partly delivered:* a failed row does not stop the others and carries the runtime's error; retry is by starting the batch again | Steps/segments report a typed outcome (`businessError` vs `systemError`); orchestrator applies different retry/backoff rules per type, configurable per script or per job | Add an `errorKind` field to step/segment results; retry logic in `LeaseExpiryMonitor`/result handling | Low-medium |
| 6 | **Role-based access control (RBAC)** — users, roles, permissions, tenants/folders | Today auth is one shared JWT signing key with no identity. Needs a `users`/`roles`/`permissions` model, login, and per-route authorization checks | New auth service or extension of the Go orchestrator with a user table, hashed passwords/OIDC, and middleware checks beyond "valid signature" | Medium-high — real but bounded work; no external dependency required beyond a DB and perhaps an identity provider (OIDC) for SSO |
| 7 | **Audit trail of user actions** (who published/edited/deleted/ran what, when) | Append-only `audit_log` table recording actor, action, target, timestamp for every mutating API call | Middleware that logs after each handler, reusing the existing `AppendSecurityEvent` pattern | Low — very close to what already exists for security events |
| 8 | **Credential vault integration** (Azure Key Vault, HashiCorp Vault, AWS Secrets Manager, CyberArk) | Backend fetches secrets from an external vault API at job-dispatch or run time, injects them as the worker's `${secret:NAME}`, never persists them | New Go module per vault (most expose a simple REST API); orchestrator calls out at job assignment | Low-medium per vault — each is a bounded API integration, no novel engineering |
| 9 | **Nested/dependent scripts as reusable libraries** (shared steps across scripts, like UiPath reusable workflows/libraries) | A script step type `callScript: {id, version, params}` that the runtime resolves by fetching and inline-executing (or orchestrator-dispatching) another published artifact | Runtime + orchestrator change: artifact fetch-and-execute, with cycle detection | Medium |
| 10 | **Human-in-the-loop task/approval queue** (UiPath Action Center: suspend a run, wait for a person to act, resume) — *partially* resolvable server-side | A `pending_actions` table; a run can suspend (`HANDEDOFF` state, which Tracto's `ContinuationMappings` already models for terminal states) and an external actor (a human via a web form) calls an API to resume it with input | Tracto's **continuations** feature already maps `triggerState: "handedoff"` to a target artifact — the chaining plumbing exists. What's missing is (a) a run actually able to pause mid-script and emit `HANDEDOFF`, and (b) a simple web form UI for a person to act on it | Medium — the hard infra (state mapping) exists; needs a pause/resume primitive in the runtimes and a minimal UI, no AI needed |
| 11 | **Structured log streaming / live tail of a running job** | WebSocket or Server-Sent-Events endpoint on the orchestrator streaming telemetry as it is appended, instead of polling `/jobs/{runId}/telemetry` | Go's `net/http` supports SSE natively; add a stream endpoint over the existing telemetry table | Low |
| 12 | **Scheduling beyond cron** (job-count ramping, "launch N jobs up to a target concurrency", time-zone-aware triggers) — *time-zone-aware cron triggers are delivered (Table 1 #17); ramping and concurrency targets are not* | Extend the existing `/admin/schedules` cron model with a strategy field and per-trigger timezone | Orchestrator-side scheduler logic change | Low-medium |
| 13 | **Native Office file manipulation (Excel cell read/write, Word content, without driving the UI)** — *the Excel part is delivered by sheet-service (Table 1 #34); Word is not* | A Go (or .NET) service that opens `.xlsx`/`.docx` directly (e.g., via an OOXML library) and exposes `excel.getCell`, `excel.setCell`, `excel.readRange` actions, bypassing the fragile UI-driving approach entirely | New runtime actions backed by a library (no AI needed — OOXML is a well-documented open format); this is arguably **better** than UiPath's own UI-driven Excel activities for headless/background jobs | Low-medium — high value, well-trodden technical ground |
| 14 | **PDF text/field extraction (non-ML, template/rule based)** — *also the first step of a loop over the invoices in a PDF: the extraction would live in a Go API that then queues a child per invoice (Table 2 #24)* | A `pdf.extractText`, `pdf.getFormField` action backed by a PDF-parsing library, for digitally-generated PDFs with a text layer (not scanned images) | New runtime action, library-backed, no model training needed | Low |
| 15 | **File system operations as native actions** (copy/move/delete/exists, currently only reachable via `cmd /c` through the Run dialog) | Add `file.copy`, `file.move`, `file.delete`, `file.exists` actions directly in the desktop runtime | Small, self-contained runtime addition | Low |
| 16 | **`clipboard.set`** (write to clipboard, complementing the existing `clipboard.get`) | One new desktop action | Pure runtime addition | Low |
| 17 | **Nested/array-aware HTTP response parsing** (UiPath can walk arbitrary JSON structures; Tracto only captures top-level fields) | Extend `http.get`/`http.post` to accept a JSONPath/dot-path expression per captured field, or expose the full parsed JSON for later dot-path access in variable expansion | Runtime change, no new service | Low-medium |
| 18 | **Desktop-app "wait until element/window appears"** (vs. fixed `delay`) | A `waitForWindow` action that polls window existence/title up to a timeout, instead of callers guessing a fixed delay | Pure runtime addition | Low |
| 19 | **Robot/worker capability tags and pools** (route jobs not just by runtime type but by machine group, OS version, installed apps) | Extend worker registration with a `tags[]` field; job requests can require tags; orchestrator matches on both runtime and tags | Schema + matching-logic change in `/jobs/pull` | Low-medium |
| 20 | **Package/script dependency graphs** (a script declaring it needs library version X) | Add a `dependencies[]` field to the artifact manifest; orchestrator validates/resolves at publish time | Versioning and resolution logic is the bulk of the work | Medium |
| 21 | **CI/CD integration (publish-on-merge from a Git pipeline)** | A CLI or REST client that wraps the existing `PUT /artifacts/{id}/versions/{ver}` call, usable from GitHub Actions/Azure DevOps | No orchestrator change needed — this is a thin client/script on top of the existing API | Very low |
| 22 | **Insights-style reporting/analytics dashboard** (run success rate, duration trends, robot utilization over time) | A reporting read-model built from the existing `runs`/`telemetry` tables, exposed via a few aggregate endpoints and a simple dashboard page in the Orchestrator UI | Backend aggregation queries + small UI; no AI needed | Medium — mostly UI/reporting effort, data already exists |
| 23 | **Process/path-level UI Automation selectors for Win32/WPF desktop apps** (not just coordinates) | Use `System.Windows.Automation` (UI Automation, already available in .NET) in the desktop runtime to target elements by `AutomationId`/`Name`/`ControlType`, as the Designer's own verification scripts already do in this project | Runtime change to the desktop host: add `click`/`type`/`getText` variants that resolve a UI Automation element instead of a screen coordinate | Medium — real engineering but entirely standard .NET APIs already proven inside this very codebase (used for Designer test verification) |
| 24 | **Item-source APIs for loops** (UiPath's For Each over a data table, a folder, a mailbox, queue items, API results) | One Go endpoint per kind of source, each reading the items once and running a child job per item, with the same behaviour as `/process/start`: refuse before starting, reply at once, one item at a time, a result recorded per item, rerun only unfinished items, progress and cancel routes. Candidates: invoice ids extracted from a PDF, files in a folder, records returned by an HTTP API, rows of a database query | New Go handlers beside `internal/process`. The Orchestrator client in `orch.go` is reused as is; the batch loop and store are written around sheet rows and would be generalised to an item key | Low-medium per source; the PDF case also needs Table 2 #14 |

## Table 3 — UiPath features that cannot be resolved by a backend/API service alone

These require perception, ML model training/hosting, licensed third-party engines, or an entirely different product category (BPM-style process modeling, market-facing app ecosystems) — not something a Go service or schema extension can produce on its own.

| # | UiPath feature | Why a backend service can't deliver it alone | What it would actually take |
|---|---|---|---|
| 1 | **Computer Vision for Citrix/VDI/RDP automation** | Requires a trained neural network that recognizes UI elements from a raw screenshot/streamed image, including inference infrastructure and labelled training data (UiPath's own CV is a hosted ML model, not a rule engine) | A real computer-vision model (or a licensed third-party one), GPU/CPU inference hosting, and a large labelled dataset of UI screenshots — a multi-month ML effort, not a backend feature |
| 2 | **OCR-based text reading from images/screenshots** | Optical character recognition is a trained model problem (even "simple" OCR engines like Tesseract are statistical models, not deterministic logic) | Integrate a third-party OCR engine (Tesseract, Google Cloud Vision, Azure Computer Vision, UiPath's own OCR service) — feasible, but it's consuming someone else's ML model, not something a Go service can "implement" from scratch |
| 3 | **Document Understanding (intelligent form/invoice/ID extraction)** | Requires trained ML extractors (and often per-customer retraining) that generalize across document layouts; UiPath trains and hosts these centrally | Buy/integrate a document-AI API (Azure Document Intelligence, Google Document AI, AWS Textract, or UiPath's own) — not buildable as an in-house Go feature without becoming an ML company |
| 4 | **AI Center — custom ML model hosting, training, and MLOps pipeline** | This *is* an ML platform: dataset versioning, training jobs (often GPU), model registry, A/B deployment | Stand up real ML infrastructure (training clusters, model serving, drift monitoring) — an entirely different kind of system than an RPA orchestrator |
| 5 | **Process Mining** (reconstruct and visualize real business processes from system event logs across unrelated enterprise systems) | Needs a process-mining algorithm (e.g., token replay, heuristic miner) plus connectors into dozens of enterprise systems (SAP, Salesforce, ServiceNow, …) to pull event logs | A dedicated process-mining engine and a library of enterprise-system connectors — a multi-year product investment on its own, unrelated to running scripts |
| 6 | **Task Mining** (passively observe real users' desktop work across an organization to auto-discover automatable tasks) | Requires an always-on desktop capture agent deployed fleet-wide, privacy/consent tooling, and a pattern-mining model that infers repeated tasks from raw interaction logs | A separate, privacy-sensitive, fleet-scale monitoring product with its own ML pipeline — out of scope for an orchestrator or runtime |
| 7 | **Agentic AI / Agent Builder / Autopilot** (LLM-driven agents that reason, call tools, and are built via natural-language chat) | Requires hosting or integrating a large language model, prompt/tool-orchestration runtime, and governance tooling (PII filtering, audit of model reasoning) — this is current-generation generative AI infrastructure, not deterministic backend logic | Integrate a hosted LLM API (as this very Designer's "AI Bridge"/MCP feature already begins to do) and build a proper agent runtime around it — a real but distinct engineering track from RPA execution |
| 8 | **Full computer-vision-based "image click"/"find image" fallback automation** | Template/feature matching against arbitrary screenshots is itself a (lighter-weight) ML/vision problem, sensitive to resolution, theming, and DPI scaling | A vision-matching library (e.g., OpenCV template matching) integrated into the desktop runtime — feasible as an *addition*, but it is a vision algorithm, not a server API, and is inherently less reliable than selector-based automation |
| 9 | **Citrix/VDI protocol-level integration** (UiPath's Citrix extension installed on the application server, decoding the ICA/RDP stream) | Requires a vendor-specific client/server extension operating inside Citrix's own protocol stack, with Citrix's cooperation/APIs | Build and certify a Citrix Virtual Channel extension — a specialized, vendor-coupled engineering effort, not something general backend work produces |
| 10 | **Enterprise SaaS connector catalog (UiPath Integration Service: hundreds of pre-built OAuth connectors for Salesforce, Workday, SAP, ServiceNow, etc.)** | Each connector requires understanding and maintaining a specific vendor's API, auth flow, and object model; UiPath maintains hundreds of these as an ongoing product | A connector framework could be *built* (Table 2-style, as new HTTP actions), but a catalog of hundreds of maintained, pre-built, certified connectors is a sustained product investment, not a one-time backend feature |
| 11 | **Marketplace ecosystem** (third-party activity packages, templates, community contributions, with review/certification) | This is a two-sided marketplace with external developers, a review process, and a distribution/discovery platform — a business/community function, not a technical capability | Not a backend problem at all — would require building a developer ecosystem and marketplace product |
| 12 | **BPMN-style process orchestration across human + robot + agent steps spanning weeks (UiPath Maestro)** | This is a long-running business-process-modeling product (case management, SLAs, escalation chains across humans and multiple automations) layered above basic job orchestration | A genuinely new product layer on top of (not instead of) the orchestrator — large, multi-quarter scope, closer to a BPM suite than an RPA backend |
| 13 | **Studio Web / browser-based low-code authoring usable by non-developers, with Autopilot chat-assisted building** | Combines a web IDE, a constrained no-code activity model, and an LLM copilot embedded in the authoring experience | A separate web application plus the same LLM-integration work as item 7 — not a Go backend task |
| 14 | **Attended robot "Picture-in-Picture" / human-and-robot share one desktop session safely** | Requires a specialized virtual-desktop/session-isolation technique so a robot can act in a session a human is also using, without visual interference | OS-level session virtualization engineering (UiPath built this as a dedicated technology) — infeasible as an API/service addition |

## Summary

- **Table 1 (34 items):** Tracto already covers the *execution primitives* of RPA well for desktop keystroke/window automation, browser automation (with real selectors, unlike its desktop side), HTTP calls, multi-runtime segmented pipelines (a genuine strength), job scheduling, artifact versioning, and basic security/signing. Most gaps even within "existing" features are depth gaps (no typed variables, no desktop selectors, no per-row decision yet) rather than absence.
- **Table 2 (24 items):** **Control flow** is the one gap that changes Tracto from "runs a fixed list of steps" to "runs a program," and it has no AI dependency. It is delivered outside the script, as a main job and a child job with a Go API between them, for every loop and every decision: the For Each row loop exists for sheets, and a branch API (If/Switch), APIs for other item sources such as a PDF, a row filter, While/until and a retry count are the next items (Table 2 #1 and #24). Close behind: **typed variables/queues/retry policies**, **desktop UI Automation selectors** (the codebase already uses UI Automation internally for its own test verification, so the capability is proven, just not exposed to scripts), **RBAC**, **vault integration**, and **native Office/PDF parsing** (which would actually be *more* reliable than UiPath's own UI-driven approach for headless jobs).
- **Table 3 (14 items):** Everything genuinely ML/perception-based (Computer Vision, OCR, Document Understanding, AI Center, Process/Task Mining, Agentic AI), everything requiring a vendor-specific protocol integration (Citrix), and everything that is actually a different *kind* of product (Marketplace, Maestro's BPM layer, Studio Web) — none of these can be delivered by extending the Go orchestrator or any single backend service; they each require either licensing/integrating someone else's ML model or building a genuinely separate product.
