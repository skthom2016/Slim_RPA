§1 — Scope and Relationship to the Architecture

The Desktop Runtime reproduces authorized human mouse, keyboard, clipboard and control interactions with Windows applications using deterministic scripts. Primary targeting is Windows UI Automation; Java Access Bridge is used for supported Java controls; keyboard navigation is an approved fallback; coordinates are allowed only relative to a UIA-identified control. There is no OCR/image targeting or arbitrary screen coordinate execution in v1.

This is one independently delivered .NET application in the Tracto Runtime family. The product has three logical components: Designer, Runtime family and Orchestrator. This document covers Part A (shared host obligations) and Part B (Desktop-specific actions, environment, failure conditions and acceptance tests).

§2 — Part A: Shared Runtime Host Obligations

v1.1 Fix — P1
All references to "CEC v1.0" updated to CEC v1.0.1. The completed Stage 1 contract packages (Tracto.Contract.*, Tracto.Conformance.*) are the normative implementation baseline. The Desktop team must import the published NuGet packages from the Stage 1 release, not a provisional v1.0 baseline.

The following host obligations are required for every worker. The canonical wire, result and condition semantics belong to the Common Execution & Orchestrator Interface Contract v1.0.1. A runtime team may share .NET libraries or implement these separately, but must pass the same conformance fixtures.

§2.0 Shared Host Contract Reference

This Runtime conforms to CEC-HOST-001 through CEC-HOST-009 in the Common Execution & Orchestrator Interface Contract v1.0.1. Those normative host requirements are defined once in the CEC. Only engine-specific obligations are specified below.

All programmatic API invocations use service.invoke to a registered independently developed custom business service. Normal UI/website/shell interactions with authorized target applications remain in scope.

§2.1 Invocation and Execution Model

  1. A configured worker advertises its runtimeType, capabilities, worker version and supported schema majors.
  2. Worker initiates authenticated outbound pull; receives a run/attempt-bound lease and immutable artifact reference.
  3. Before side effects, verify signatures, input types, environment permissions, policy refs and workload compatibility.
  4. Execute runtime-specific steps with bounded deadlines, technical pre/postconditions and action status evidence.
  5. Handle a synchronous registered custom-service response or an acknowledged asynchronous handoff; never call third-party business APIs directly or make business decisions.
  6. Write local run journal and send final result. Reconcile after disconnect; release job capacity and runtime-specific resources.

§2.2 Worker/Session and Deployment Assumptions

One job per registered bot worker in v1. Worker processes are separate applications; multiple workers may share a host only where capacity and session/input isolation allow. Isolated deployment uses the single Windows Runtime Host Supervisor to supervise WSL2/Docker/Orchestrator. Host/interactive-session POC-01–POC-10 gates remain those of architecture v1.2A.

§4 — Desktop Application and Session Lifecycle

DES-001 Session eligibility
Requirement

Verify authorized interactive logon, active input desktop, process identity, lock state and session class before GUI input.

Acceptance

Given locked, logged-off, disconnected or noninteractive session, no click/key injection occurs and a stable SESSION_UNAVAILABLE result is returned.

DES-002 Display baseline
Requirement

Validate single active monitor and configured fixed resolution/DPI against certified environment at run admission and after major UI changes.

Acceptance

Resolution or DPI drift blocks control-relative coordinates with DISPLAY_PROFILE_CHANGED; UIA-only actions may follow explicit policy.

DES-003 Foreground ownership
Requirement

Acquire exclusive input lease per interactive desktop session and verify active target foreground before each input phase.

Acceptance

Two workers cannot interleave input in one session; focus theft fails safely without typing into unrelated application.

DES-004 Application launch and attach
Requirement

Launch a policy-allowlisted executable/shortcut with arguments or attach using process identity and window ownership.

Acceptance

Correct PID/window is attached even when identical titles exist; unauthorized executable returns policy error.

DES-005 Window enumeration
Requirement

Discover owned top-level/child windows, visibility, bounds, enabled/focused state and modal ownership.

Acceptance

Finds main window and nested modal in WinForms/WPF fixture; ambiguous matches surface candidates instead of guessing.

DES-006 Window state control
Requirement

Activate, bring to front, restore, maximize, minimize, move and resize windows where OS permits.

Acceptance

Each action verifies resulting state within bounded timeout; denial returns WINDOW_CONTROL_FAILED.

DES-007 Application exit handling
Requirement

Detect normal process exit, crash, freeze and owned child-process changes, with configured close/relaunch policy.

Acceptance

Unexpected exit before postcondition never yields SUCCEEDED; evidence identifies missing process.

DES-008 Unexpected modal handling
Requirement

Recognize configured dialogs or stop with diagnostic; never blindly dismiss arbitrary security or update prompts.

Acceptance

Injected unrelated modal blocks action and is reported with sanitized window metadata.

DES-009 User interference
Requirement

Detect foreground theft and competing physical mouse/keyboard input under unattended mode and apply policy (pause/fail).

Acceptance

Human activity causes controlled suspension/failure without corrupting later steps.

DES-010 Supervisor integration
Requirement

Desktop interactive executor receives host/session readiness via authorized local IPC; shared Supervisor owns WSL start and availability in isolated mode.

Acceptance

Background Supervisor cannot inject desktop events; executor runs only in correct user session and owns job pull/heartbeat.

§5 — Element Identification and State Targeting

UIA-001 Stable UIA queries
Requirement

Select targets by AutomationId, ControlType, Name, ClassName, ancestor/window/process context and available patterns.

Acceptance

Button selection survives window movement and control-relative layout changes.

UIA-002 Unique target enforcement
Requirement

Require one unambiguous accessible target or explicit, stable scoped selector/index within named container.

Acceptance

Two identical buttons without disambiguation yield TARGET_AMBIGUOUS without action.

UIA-003 Re-resolution after redraw
Requirement

Invalidate cached element references when provider reports stale or window refreshes; re-find using selector. This is internal Runtime behavior — not a script step.

Acceptance

Fixture re-renders list and selected control can be re-found without stale COM object crash.

UIA-004 Visibility and enabled checks
Requirement

Verify control exists, is visible and enabled, in foreground ownership and not occluded when pointer input is required.

Acceptance

Disabled or offscreen control is waited for or reported; no blind click.

UIA-005 UIA pattern preference
Requirement

Use Invoke, Value, Selection, Toggle, ExpandCollapse, Scroll and other supported UIA patterns where appropriate.

Acceptance

A checkbox is set to target state without unintended toggle when already checked.

UIA-006 Java accessibility adapter
Requirement

Support explicitly certified Java Access Bridge applications and exposed names/roles/states/actions.

Acceptance

Swing fixture button, editable field and tree are addressed with stable Java accessibility identity.

UIA-007 Keyboard fallback
Requirement

Use documented tab order, accelerators and navigation when semantic element controls are unavailable.

Acceptance

Fixture responds to known hotkey path and asserted state without absolute cursor coordinates.

UIA-008 Control-relative pointer fallback
Requirement

Allow bounded offsets only from freshly located UIA control with verified rectangle, foreground, DPI and hit region. Java Access Bridge location alone is insufficient to authorize coordinate input — see §11.

Acceptance

An offset remains inside the anchored UIA control after moving the window; missing UIA anchor blocks action.

UIA-009 No visual targeting
Requirement

Reject OCR/image confidence selectors, screenshot-coordinate selectors and arbitrary absolute screen click actions.

Acceptance

Validation rejects unsupported selector class before job begins.

UIA-010 Virtualized/scrollable controls
Requirement

Scroll to target via element/scroll patterns or bounded keyboard paths and re-resolve after realization. This scrolling is internal Runtime behavior triggered by any action that needs to locate the element.

Acceptance

Virtualized grid row reached, targeted and verified in reference app.

UIA-011 Accessibility provider failure
Requirement

Surface TIMEOUT / UNSUPPORTED_CONTROL / ACCESS_DENIED instead of silently converting to arbitrary coordinates.

Acceptance

Opaque custom control without accessible/keyboard path is a documented clean failure.

§6 — Human-Equivalent Input Actions

INPUT-001 Mouse movement and clicking
Requirement

Provide move, left/right/middle click, double click, button down/up and context-menu invocation on verified target.

Acceptance

Reference app logs proper target, click count and button with no out-of-window input.

INPUT-002 Drag and drop
Requirement

Press, move along configured bounded path, release and verify resulting UI state; always release input on cancellation.

Acceptance

Drag item between panes completes; forced cancellation leaves no held mouse button.

INPUT-003 Hover and scrolling
Requirement

Dwell on verified control to open contextual UI (via dwellMs on desktop.mouse.move); support vertical/horizontal wheel and UIA ScrollPattern.

Acceptance

Nested menu opens after dwell and list scroll affects intended pane only.

INPUT-004 Unicode typing
Requirement

Enter Unicode/multiline text and keyboard shortcuts with defined keyboard layout/IME handling; release modifier keys.

Acceptance

Accented/non-Latin test strings and Ctrl/Alt/Shift shortcuts work in certified editors.

INPUT-005 Text entry strategy
Requirement

Prefer UIA ValuePattern where supported; otherwise controlled typing or clipboard paste under declared policy.

Acceptance

Target field receives exact expected value; chosen strategy is reported.

INPUT-006 Clipboard isolation
Requirement

Read/write permitted clipboard text, handle clipboard-lock contention and restore supported prior contents when policy requires. Restoration is a script-authored sequence using existing clipboard actions — not an atomic single action.

Acceptance

Busy clipboard gets bounded retry; prior text is restored and unsupported proprietary formats are disclosed.

INPUT-007 Copy-paste workflow
Requirement

Select UI text, copy to controlled buffer, map it to output/API input and paste approved returned data into target UI.

Acceptance

Extracted text exactly matches fixture; API response is pasted unmodified without domain calculation.

INPUT-008 Hotkey and key-hold cleanup
Requirement

Support keydown/up, key combinations, repeat count and timeout-aware release in any failure path.

Acceptance

Cancelled Ctrl+Shift sequence leaves neither modifier logically pressed.

INPUT-009 Sensitive text input
Requirement

Resolve secretRef only on Windows, suppress keystroke/clipboard secret echo in evidence and clear owned sensitive transient buffers.

Acceptance

Secret fills auth control; no plaintext appears in logs, screenshots or Orchestrator messages.

§8 — Waiting, Failures and Safe Recovery

REC-001 Explicit state waits
Requirement

Wait for visible, enabled, focused, text-equals technical navigation state, window creation/destruction and app ready conditions.

Acceptance

Slow-load fixture succeeds without arbitrary fixed delay; timeout ends with code and evidence.

REC-002 Postcondition verification
Requirement

Every potentially consequential UI action must have observable app-state assertion or explicit unknown completion policy.

Acceptance

Click with no confirmed change is not automatically reported SUCCEEDED.

REC-003 Focus theft and overlay
Requirement

After waits, recheck foreground, target bounds and overlay/modal presence before sending input.

Acceptance

Injected overlay blocks action and no unrelated input occurs.

REC-004 Irreversible action uncertainty
Requirement

When Save/Submit may have succeeded but response is lost, record run state UNKNOWN with unknownReason: action.commitUncertain; do not automatically repeat unless idempotence is proven.

Acceptance

ERP save timeout results in UNKNOWN + needsAttention=true and no second Save.

REC-005 Cancellation and cleanup
Requirement

On cancel/timeouts release held keys/buttons, transient clipboard handles, session input lease and owned process handles.

Acceptance

Kill during drag or hotkey does not leave desktop unusable.

REC-006 Window/application crash
Requirement

Detect hung/crashed app, collect safe evidence and execute only approved restart/recovery step.

Acceptance

Injected crash reports APP_CRASH (errorCategory: ENVIRONMENT) and optional safe relaunch without duplicating submission.

REC-007 Selector failure diagnostics
Requirement

Return missing/ambiguous/stale/unsupported provider codes, attempted selector strategy and sanitized bounds.

Acceptance

Engineer can identify failing control without retaining secret input.

REC-008 User lock/disconnect recovery v1.1 clarified
Requirement

Pause or fail safely when the interactive session is locked, logged off or disconnected. Any paused run retains a bounded pause deadline (default 5 minutes, configurable by approved policy), then exits as FAILED, TIMED_OUT or UNKNOWN according to side-effect evidence.

v1.1 Clarification — P2
This bounded wait is an internal behavior under the RUNNING state — no PAUSED run state is introduced. Heartbeat continues during the wait period and counts toward the lease deadline. On deadline expiry, the run exits through the normal FAILED, TIMED_OUT, or UNKNOWN path per Common Contract C3 rules, depending on whether the last consequential action's side effect can be established. The 5-minute default is a configurable policy value, not an immutable architectural constant.
Acceptance

Lock screen mid-run yields defined FAILED or UNKNOWN outcome depending on last action; RUNNING state is maintained throughout; no PAUSED state is emitted.

REC-009 Service outcome routing
Requirement

Map service outcome category or allowlisted actionCode to predefined UI steps; do not compare business amounts.

Acceptance

Rejected invoice status is rendered as given; amount threshold expressions are rejected.

§11 — Desktop Selector and Target Schema (Normative)

v1.1 Fix — P2
relativePoint may only be anchored to a UIA-located control. Java Access Bridge enables semantic actions and keyboard fallback for Java applications; it does not authorize coordinate-based input. The phrase "UIA/Java-located" in v1.0 has been corrected to "UIA-located" throughout this section.

Selectors are stable logical targets, not captured click coordinates. Resolution chain: executable/process identity → top-level window → zero or more ancestor controls → leaf control. RuntimeId, volatile window handles and arbitrary absolute screen coordinates must never be persisted as long-term selectors.

Appendix A — Desktop Error Code to Contract errorCategory Mapping ★
New in v1.1 — P1 correction
Desktop-specific error identifiers must be mapped to the Common Contract errorCategory enum. UNKNOWN_OUTCOME (used in v1.0 action catalogue) is not an error code — it was conflated with the run/step state UNKNOWN. The correct pattern: when a consequential action's side effect cannot be established, the step/run state is UNKNOWN and unknownReason carries a C3-approved stable code. The errorCategory on the step describes the class of failure that led to the uncertainty.
